# 한화 고객 페인포인트 해결 AI 프로젝트 기획안

## 1. 과제 개요

한화그룹의 주요 사업과 서비스를 이용하는 고객의 관점에서 불편하거나 개선이 필요한 순간을 찾고, 이를 AI를 활용한 새로운 서비스 또는 해결책으로 제안한다.

### 과제에서의 역할

`TF`는 `Task Force`의 약자로, 특정 문제를 해결하기 위해 한시적으로 구성된 프로젝트팀을 의미한다.

본 프로젝트에서는 **한화그룹 고객경험 혁신 TF**의 관점에서 다음 업무를 수행한다.

1. 고객 설문 데이터 분석
2. 주요 고객 불편사항 발견
3. 불편사항의 원인 분석
4. AI 기반 해결책 설계
5. 간단한 서비스 프로토타입 구현
6. 기대효과와 현업 적용방안 제시

---

## 2. 프로젝트 주제

### 프로젝트명

**한화생명 Easy Guide AI**

고객의 질문과 상황을 분석하여 금융상품의 보장 내용, 상품 간 차이, 갱신 조건 및 주의사항을 쉬운 말로 설명하는 AI 서비스

### 프로젝트 목표

보험 및 금융상품을 이용하는 고객은 다음과 같은 어려움을 경험할 수 있다.

- 보험 전문용어가 어렵다.
- 상품의 보장 내용을 이해하기 어렵다.
- 상품 간 차이를 비교하기 어렵다.
- 갱신형과 비갱신형의 차이를 이해하기 어렵다.
- 보장되지 않는 조건을 찾기 어렵다.
- 자신에게 필요한 보장이 무엇인지 판단하기 어렵다.
- 상담 시 무엇을 질문해야 할지 모르겠다.

본 프로젝트는 설문 데이터에서 실제 고객 불편사항을 발견하고, 공식 상품 정보를 기반으로 고객의 질문에 답변하는 AI 서비스를 제안하는 것을 목표로 한다.

> 실제 설문 데이터가 금융상품과 관련된 데이터인지 먼저 확인한다.  
> 설문이 여러 한화 서비스에 관한 데이터라면 금융 분야 응답만 분석하거나, 가장 많이 나타난 서비스 영역을 프로젝트 주제로 선택한다.

## 3. 핵심 프로젝트 구조

전체 프로젝트는 다음과 같은 흐름으로 진행한다.

> 설문 데이터 정리  
> → 고객 불편사항 분류 및 클러스터링  
> → 핵심 문제의 우선순위 선정  
> → 문제의 근본 원인 분석  
> → AI 서비스 기능 설계  
> → 금융상품 데이터 연결  
> → 고객 질문 분류 및 답변 생성  
> → 간단한 웹앱 프로토타입 구현

각 데이터와 AI의 역할은 다음과 같이 구분한다.

- **설문 데이터:** 무엇을 해결해야 하는지 결정
- **상품 데이터:** 고객 질문에 어떤 내용으로 답변할지 결정
- **LLM:** 설문 및 상품 정보를 고객이 이해하기 쉬운 문장으로 변환
- **프로토타입:** 분석 결과가 실제 고객 서비스로 연결되는 모습을 시연

## 4. 필요한 데이터

### 4.1 금융상품 데이터

설문 데이터만으로는 구체적인 상품 질문에 정확하게 답변하기 어렵다. 따라서 별도의 금융상품 정보가 필요하다.

| 항목 | 설명 |
|---|---|
| 상품명 | 상품의 이름 |
| 상품 유형 | 건강보험, 암보험, 종합보험 등 |
| 주요 보장 | 상품이 보장하는 주요 항목 |
| 보장 제외 조건 | 보장되지 않는 상황 |
| 갱신 여부 | 갱신형 또는 비갱신형 |
| 보험료 예시 | 고객 이해를 위한 예시 금액 |
| 추천 대상 | 상품이 적합할 수 있는 고객군 |
| 주의사항 | 가입 전에 확인해야 하는 내용 |
| 근거 문서 | 상품 설명서 또는 공식 자료 |
| 정보 기준일 | 상품 정보가 갱신된 날짜 |

프로토타입 단계에서는 실제 상품 전체를 수집할 필요 없이 상품 3개 정도만 구성해도 된다.

실제 상품 정보를 확보하기 어렵다면 가상의 상품 데이터를 만들고 다음과 같이 표시한다.

> 본 상품 정보는 서비스 구조 검증을 위한 프로토타입용 예시 데이터입니다.  
> 실제 서비스 적용 시 한화생명의 공식 상품 설명서 및 내부 상품 데이터와 연동합니다.

### 상품 데이터 예시

```json
{
  "product_id": "P001",
  "name": "한화 케어플랜 A",
  "type": "건강보험",
  "target": "사회초년생",
  "coverage": [
    "암 진단",
    "질병 입원"
  ],
  "exclusions": [
    "일부 경미 질환",
    "약관에서 제외한 기존 질환"
  ],
  "renewal": "갱신형",
  "premium_example": "월 35,000원",
  "caution": "갱신 시 보험료가 변동될 수 있습니다.",
  "source": "프로토타입용 상품 설명서"
}
```

### 4.2 고객 설문 데이터

설문 데이터는 고객이 어떤 불편을 겪고 있는지 분석하기 위해 사용한다.

| 항목 | 설명 |
|---|---|
| 고객 불편 내용 | 고객이 작성한 자유응답 |
| 이용 서비스 | 보험, 금융상품 등 |
| 불편 발생 단계 | 정보 탐색, 비교, 가입, 상담 등 |
| 불편 심각도 | 고객이 느낀 불편의 정도 |
| 고객 특성 | 연령대, 가족 구성, 이용 경험 등 |
| 이용 채널 | 모바일, 웹, 전화, 오프라인 |
| 재이용 의향 | 불편이 실제 행동에 미친 영향 |
| 상담 의향 | 상담 필요 여부 |

설문 데이터는 고객 불편사항을 발견하고 해결 우선순위를 선정하는 데 사용한다.

#### 설문 분석 결과 파일: `data/survey_analysis.json`

`survey_analysis.json`은 설문 원문이 아니라 `analyze_data.py`가 생성한 설문 분석 요약 결과입니다. `app.py`는 이 파일을 읽어 설문 지표, 그래프, 설문 우선순위, 상품 추천 근거를 표시합니다.

최상위 구조는 다음과 같습니다.

```json
{
  "method": "TF-IDF(word+char n-grams) + KMeans + 세부 키워드 라벨링",
  "n_rows": 1000,
  "n_clusters": 8,
  "n_labeled_clusters": 6,
  "random_state": 42,
  "label_taxonomy": {
    "정보 이해": ["전문용어 이해", "보장 범위 이해"],
    "상품 비교": ["상품 보장 비교", "보험료 비교"],
    "주의사항": ["보장 제외 조건", "갱신 조건"],
    "상담": ["상담 질문 준비", "상담 정보 전달"]
  },
  "clusters": []
}
```

| 키 | 설명 |
|---|---|
| `method` | 사용한 분석 방법 |
| `n_rows` | 분석한 설문 응답 수 |
| `n_clusters` | K-means가 생성한 원본 군집 수 |
| `n_labeled_clusters` | 동일한 상위·세부 라벨을 통합한 뒤 표시하는 군집 수 |
| `random_state` | K-means 재현성을 위한 난수 시드 |
| `label_taxonomy` | 상위 유형과 세부 불편 라벨의 분류 체계 |
| `clusters` | 군집별 요약 결과 배열 |

`clusters` 배열의 각 항목에는 다음 정보가 들어 있습니다.

| 필드 | 설명 |
|---|---|
| `cluster_id` | 원본 K-means 군집 식별자 |
| `label` | 세부 불편 유형 라벨 |
| `parent_label` | 세부 라벨의 상위 유형 |
| `merged_cluster_count` | 같은 라벨로 통합된 원본 군집 수 |
| `label_confidence` | 군집 내 대표 라벨이 차지하는 비율 |
| `count` | 해당 불편 유형의 응답 수 |
| `ratio` | 전체 응답 중 해당 유형의 비율 |
| `avg_severity` | 해당 유형의 평균 불편 심각도(1~5점) |
| `top_terms` | TF-IDF 기준 대표 표현 |
| `representative_complaints` | 군집을 대표하는 응답 예시 |
| `keyword_label_distribution` | 군집 안의 세부 라벨별 응답 분포 |
| `synthetic_reference_label` | 가상 데이터 생성 시 참고한 기준 라벨 |

`n_clusters`는 K-means 원본 군집 수이고, `n_labeled_clusters`와 `clusters` 배열 길이는 동일한 상위·세부 라벨을 통합한 뒤 화면에 표시되는 결과 수입니다. `synthetic_reference_label`은 프로토타입용 가상 데이터 검증을 위한 참고값이며, 실제 고객 데이터 분석의 입력값으로 사용하지 않습니다.

## 5. 설문 데이터 분석 방법

### 5.1 데이터 전처리

자유응답에서 불필요한 표현과 중복 응답을 정리한다.

- 결측값 확인
- 중복 응답 제거
- 오탈자 및 표현 통일
- 개인정보 제거
- 짧거나 의미 없는 응답 분리
- 서비스 및 고객 여정 단계 분류

### 5.2 불편사항 클러스터링

자유응답을 유사한 의미끼리 묶는다.

예상 가능한 불편 유형은 다음과 같다.

1. 전문용어 이해
2. 보장 범위 이해
3. 상품 보장 비교
4. 보험료 비교
5. 보장 제외 조건
6. 갱신 조건
7. 상담 질문 준비
8. 상담 정보 전달

실제 구현에서는 위 불편을 다음 8개 세부 라벨로 분류하고, 같은 상위·세부 라벨로 나뉜 군집은 분석 결과에서 통합한다. 각 라벨의 응답 수, 응답 비율, 평균 심각도, 대표 표현과 대표 응답은 `data/survey_analysis.json`에 저장한다.

클러스터링은 키워드 분석, 문장 임베딩, 유사도 분석 또는 LLM 분류를 활용할 수 있다.

각 클러스터에는 다음 정보를 함께 표시한다.

- 응답 건수
- 전체 응답 중 비율
- 평균 불편 심각도
- 주요 고객군
- 대표 응답
- 고객 행동에 미친 영향

### 5.3 가상 분석 예시

아래 수치는 프로젝트 구조를 설명하기 위한 예시이며, 실제 발표에서는 설문 데이터에서 계산한 값을 사용한다.

| 클러스터 | 주요 불편 | 응답 수 | 평균 심각도 | 주요 고객 |
|---|---|---:|---:|---|
| A | 보험 용어와 보장 내용이 어려움 | 380명 | 4.3/5 | 첫 보험 가입자 |
| B | 상품 간 차이를 비교하기 어려움 | 270명 | 4.0/5 | 20~40대 고객 |
| C | 보장 제외 조건을 찾기 어려움 | 210명 | 4.4/5 | 기존 보험 보유자 |
| D | 상담 전에 질문을 준비하기 어려움 | 140명 | 3.2/5 | 모바일 이용자 |

이 결과를 통해 다음과 같은 핵심 인사이트를 도출할 수 있다.

> 고객은 상품 정보가 없어서 불편한 것이 아니라, 상품 정보를 이해하고 비교하기 어려워서 불편을 겪고 있다.

또한 A와 B 클러스터는 다음과 같이 연결된다.

> 어려운 보험 용어  
> → 보장 내용 파악의 어려움  
> → 상품 간 비교의 어려움  
> → 가입 또는 상담 지연

### 5.4 해결 우선순위 선정

모든 불편사항을 한 번에 해결하기보다 가장 중요한 문제를 선정한다.

> 문제 우선순위 = 발생 빈도 × 불편 심각도 × 사업 영향도

예시는 다음과 같다.

| 불편 유형 | 발생 빈도 | 심각도 | 사업 영향 | 우선순위 |
|---|---:|---:|---:|---:|
| 보험 용어 이해 어려움 | 높음 | 높음 | 가입 이탈 | 1순위 |
| 상품 비교 어려움 | 중간 | 높음 | 상담 의존 증가 | 2순위 |
| 보장 제외 조건 확인 어려움 | 중간 | 높음 | 고객 불안 증가 | 3순위 |
| 상담 준비 어려움 | 중간 | 중간 | 상담시간 증가 | 4순위 |

본 프로젝트에서는 A, B, C 클러스터를 해결하기 위해 **금융상품 설명·비교 AI**를 핵심 솔루션으로 선정한다.

## 6. 문제 정의 및 원인 분석

### 핵심 문제 정의

> 한화생명 고객은 상품 정보를 제공받고 있지만, 전문용어와 복잡한 보장 조건으로 인해 상품의 차이를 이해하지 못하고 자신에게 필요한 상품인지 판단하기 어렵다.

### 근본 원인

#### 1. 어려운 전문용어

- 보험 및 금융 전문용어가 많이 사용된다.
- 설명이 고객의 일상적인 상황과 연결되지 않는다.

#### 2. 정보의 분산

- 보장 내용과 제외 조건이 여러 문서에 나뉘어 있다.
- 고객이 여러 상품을 동일한 기준으로 비교하기 어렵다.

#### 3. 개인화 부족

- 동일한 설명이 모든 고객에게 제공된다.
- 고객의 연령, 가족 구성, 기존 보험 상황이 충분히 반영되지 않는다.

#### 4. 상담 준비 부족

- 고객이 상담 전에 기본 내용을 이해하기 어렵다.
- 어떤 항목을 상담사에게 확인해야 하는지 알기 어렵다.

### 핵심 인사이트

> 고객의 문제는 정보가 없는 것이 아니라, 정보가 고객의 언어와 상황에 맞게 구조화되어 있지 않다는 점이다.

## 7. 설문 분석 결과와 기능의 연결

설문 분석은 단순한 배경 자료가 아니라 서비스 기능을 결정하는 기준이 된다.

| 설문에서 발견한 사실 | 고객 문제 해석 | 해결 기능 | 검증 지표 |
|---|---|---|---|
| 보험 용어가 어렵다는 응답이 많음 | 설명서가 고객 언어와 맞지 않음 | 쉬운 말 설명 AI | 고객 이해도 점수 |
| 상품 비교가 어렵다는 응답이 많음 | 동일한 기준으로 비교하기 어려움 | 상품 비교표 | 비교 완료율 |
| 제외 조건을 찾기 어렵다는 응답이 많음 | 보장 범위에 대한 불안이 큼 | 보장 제외·주의사항 강조 | 관련 문의 감소 |
| 상담 질문을 준비하기 어렵다는 응답이 있음 | 상담 전 이해와 준비가 부족함 | 상담 질문 자동 생성 | 상담시간 감소 |
| 첫 가입자에게 불편이 집중됨 | 금융상품 경험이 부족함 | 초보자용 단계별 설명 | 첫 가입자 만족도 |

따라서 기능은 “AI로 구현할 수 있기 때문에” 만드는 것이 아니라, **설문에서 발견된 고객 불편을 해결하기 위해 필요하다**고 설명한다.

## 8. AI 서비스 구성

### 8.1 고객 질문 유형 분류

고객의 질문을 미리 정의한 유형 중 하나로 분류한다.

| 질문 유형 | 질문 예시 |
|---|---|
| 용어 설명 | “갱신형이 무엇인가요?” |
| 보장 설명 | “암 진단을 받으면 어떤 보장을 받나요?” |
| 상품 비교 | “상품 A와 상품 B의 차이는 무엇인가요?” |
| 제외 조건 확인 | “어떤 경우에는 보장을 받을 수 없나요?” |
| 고객 상황 안내 | “사회초년생은 어떤 보장을 확인해야 하나요?” |
| 상담 준비 | “상담사에게 무엇을 물어봐야 하나요?” |

질문 유형은 설문에서 자주 발견된 불편사항을 기준으로 선정한다.

### 8.2 AI 답변 생성 과정

1. 고객이 질문을 입력한다.
2. AI가 질문 유형을 분류한다.
3. 질문에서 상품명과 주요 키워드를 추출한다.
4. 관련 상품 데이터를 검색한다.
5. 검색된 상품 정보만 LLM에 전달한다.
6. LLM이 쉬운 말로 답변을 생성한다.
7. 답변과 함께 근거 문서와 주의사항을 표시한다.

### 예시

> 고객 질문: 상품 A와 상품 B의 차이는 무엇인가요?  
> 질문 유형: 상품 비교  
> 검색 데이터: 상품 A와 B의 보장, 갱신 여부, 보험료, 주의사항  
> AI 출력: 두 상품의 차이를 표와 쉬운 문장으로 설명

### 8.3 LLM의 역할

#### 분석 지원 역할

- 설문 자유응답 분류
- 고객 불편사항 요약
- 클러스터별 대표 키워드 추출
- 고객 페르소나 작성
- 원인 분석 아이디어 생성

#### 고객 서비스 역할

- 금융 전문용어를 쉬운 말로 변환
- 상품의 보장 내용 요약
- 상품 간 차이 비교
- 고객이 확인해야 할 주의사항 정리
- 상담 전에 물어볼 질문 생성

LLM은 상품 정보를 기억에 의존하여 답변하지 않고, 별도로 제공된 상품 데이터 안에서만 답변하도록 구성한다.

## 9. 서비스 주요 기능

### 기능 1. 고객 상황 입력

- 연령대
- 가족 구성
- 가장 걱정되는 질병 또는 사고
- 기존 보험 가입 여부
- 월 납입 희망 금액

### 기능 2. 고객 유형 분석

입력한 정보를 바탕으로 고객 유형을 보여준다.

예시:

> 사회초년생·기본 보장 점검 필요형

### 기능 3. 쉬운 상품 설명

상품 정보를 다음 형식으로 제공한다.

- 한 줄 요약
- 보장되는 상황
- 보장되지 않는 상황
- 갱신 여부
- 보험료 예시
- 가입 전 주의사항
- 근거 문서

### 기능 4. 상품 비교

상품 2~3개를 같은 기준으로 비교한다.

| 비교 항목 | 상품 A | 상품 B |
|---|---|---|
| 주요 보장 | 암 진단 및 입원 | 질병 및 상해 |
| 갱신 여부 | 갱신형 | 비갱신형 |
| 보험료 | 상대적으로 낮음 | 초기 보험료가 높을 수 있음 |
| 추천 대상 | 초기 보험 가입자 | 종합 보장 희망자 |
| 주의사항 | 갱신 시 보험료 변동 | 가입 초기 비용 확인 필요 |

### 기능 5. 상담 전 질문 추천 및 작성

AI가 고객의 상황과 선택한 상품을 바탕으로 상담 전에 확인하면 좋은 질문을 추천한다.

고객은 추천 질문을 선택하거나 직접 질문을 추가할 수 있다.

- 추천 질문 선택
- 질문 내용 수정
- 직접 질문 입력
- AI에게 사전 답변 요청
- 상담사에게 전달할 질문 목록 저장

## 10. 간단한 프론트엔드 구현 방법

### 구현 형태

네이티브 모바일 앱보다 **Streamlit 기반 단일 페이지 웹앱**으로 구현한다.

이 방식을 선택하는 이유는 다음과 같다.

- Python 파일 하나로 구현 가능
- 별도의 프론트엔드·백엔드 개발 불필요
- 설문 분석 차트와 AI 기능을 한 화면에 구현 가능
- 발표 현장에서 바로 실행 가능
- 고객 입력부터 결과 확인까지 시연 가능

### 최소 화면 구성

#### 1. 고객 정보 입력 영역

- 연령대
- 가족 구성
- 관심 보장
- 월 예산
- 분석하기 버튼

#### 2. AI 분석 결과 영역

- 고객 유형
- 주요 필요 보장
- 추천 상품 카드 2~3개
- 상품 비교 표

#### 3. 쉬운 설명 영역

질문 버튼 예시:

- 갱신형이 무엇인가요?
- 이 상품의 단점은 무엇인가요?
- 상품 A와 B의 차이는 무엇인가요?
- 상담사에게 무엇을 물어봐야 하나요?

질문을 선택하면 미리 작성된 답변 또는 LLM이 생성한 답변을 표시한다.

### MVP 최소 구현 범위

- 설문 분석 막대그래프 1개
- 고객 정보 선택 기능
- 고객 유형 출력
- 상품 추천 카드 2~3개
- 상품 비교 표
- 질문 선택 또는 입력 기능
- AI 설명 결과
- 근거 자료 및 주의사항 표시

로그인, 결제, 데이터베이스, 실제 가입 기능은 구현하지 않는다.

### 파일 구조 예시

```text
project/
├─ app.py
├─ analyze_data.py
├─ generate_data.py
├─ data/
│  ├─ survey_results.csv
│  ├─ survey_analysis.json
│  └─ products.json
└─ assets/
   └─ logo.png
```

### 실행 방법

```bash
# 운영 API
uvicorn main:app --reload --port 8000
```

아래 명령은 기존 Streamlit 검증 화면을 확인할 때만 사용한다.

```bash
pip install -r requirements-streamlit.txt
streamlit run app.py
```

`app.py`는 저장된 `data/survey_analysis.json`을 우선 사용한다. 파일이 없거나 예전 분석 결과이면 `analyze_data.py`의 분석 함수를 자동 실행하며, 데이터가 변경된 경우에는 화면의 `설문 분석 다시 실행` 버튼으로 수동 갱신할 수 있다.

## 11. 프로토타입 동작 시나리오

1. 고객이 연령대와 가족 구성을 선택한다.
2. 고객이 관심 있는 보장을 선택한다.
3. 시스템이 고객 유형을 표시한다.
4. 관련 상품 2~3개를 보여준다.
5. 고객이 상품을 선택한다.
6. AI가 보장 내용과 주의사항을 쉬운 말로 설명한다.
7. 고객이 두 상품을 비교한다.
8. AI가 상담 시 확인할 질문을 정리한다.
9. 고객이 상담 신청 화면으로 이동한다.

### 시연 예시

> 고객 상황  
> 20대 후반, 1인 가구, 기존 보험 없음, 월 예산 5만 원 이하

> AI 분석 결과  
> 사회초년생·기본 보장 점검 필요형

> AI 안내  
> 상품 A는 초기 보험료 부담이 비교적 낮지만 갱신 시 보험료가 변경될 수 있습니다. 상품 B는 초기 보험료가 높을 수 있지만 비갱신형이므로 장기적인 보험료 변동 여부를 함께 비교해야 합니다.

> 상담 전 확인 질문  
> 1. 갱신 시 보험료가 얼마나 변동될 수 있나요?  
> 2. 기존 질환과 관련된 보장 제외 조건이 있나요?  
> 3. 중도 해지 시 환급금은 어떻게 계산되나요?

## 12. 신뢰성 및 안전장치

금융 분야에서는 AI가 잘못된 정보를 제공하지 않도록 다음 원칙을 적용한다.

- 공식 상품 문서 또는 등록된 상품 데이터만 사용
- 답변마다 근거 문서 표시
- 상품 데이터에 없는 내용은 추측하지 않음
- 확실하지 않은 질문은 상담 연결 안내
- AI가 최종 가입 여부를 결정하지 않음
- 실제 상품 추천과 일반 정보 안내를 구분
- 개인정보는 최소한으로 입력
- 상품 정보의 기준일 표시

화면에는 다음과 같은 안내 문구를 표시한다.

> 본 서비스는 금융상품의 이해를 돕기 위한 정보 안내 서비스입니다.  
> AI의 답변은 가입 권유 또는 최종적인 금융 판단을 대신하지 않습니다.  
> 정확한 보장 내용은 공식 상품 설명서와 전문 상담을 통해 확인해야 합니다.

## 17. 프로젝트 핵심 결론

본 프로젝트는 설문 데이터를 통해 고객 불편사항을 분류하고 우선순위를 선정한 뒤, 선택된 문제를 해결하기 위한 LLM 기반 금융상품 설명 서비스를 구현한다.

설문 데이터는 **무엇을 해결해야 하는지**를 결정하고, 상품 데이터는 **어떤 내용으로 답변해야 하는지**를 결정하며, LLM은 해당 정보를 **고객이 이해하기 쉬운 형태로 전달하는 역할**을 수행한다.

최종적으로 다음 구조의 프로토타입을 구현한다.

> 고객 정보 및 질문 입력  
> → 고객 질문 유형 분류  
> → 관련 상품 데이터 검색  
> → LLM 기반 쉬운 설명 생성  
> → 상품 비교 및 주의사항 안내  
> → 상담 전 질문 정리

이때 설문 분석 결과는 단순한 배경 설명이 아니라 다음 항목을 결정하는 핵심 근거로 사용한다.

1. 해결할 핵심 고객 문제
2. 주요 타깃 고객
3. 지원할 질문 유형
4. 필요한 상품 데이터 항목
5. 구현할 AI 기능
6. 프로토타입 화면 구성
7. 성과 측정 KPI

이를 통해 데이터 분석, AI 활용, 고객경험 개선, 현업 적용 가능성을 하나의 프로젝트 안에서 논리적으로 제시할 수 있다.

## 18. FastAPI·React 마이그레이션 구조

기존 `app.py`는 삭제하지 않고 선택적인 로컬 검증용으로 유지한다. 실제 운영·Render 배포 경로는 Streamlit 없이 React 정적 사이트와 FastAPI API 서버만 사용한다.

```text
app.py                 # 기존 Streamlit 앱
main.py                # FastAPI API 서버
core/logic.py          # 추천·설문 우선순위·질문·답변 공통 로직
data/                  # 기존 상품·설문 데이터
frontend/              # React + Vite 화면
render.yaml            # Render 백엔드·프론트 배포 설정
```

### API

`GET /health`, `GET /api/products`, `POST /api/recommendations`, `POST /api/comparisons`, `POST /api/questions/recommend`, `POST /api/questions/answer`, `POST /api/questions/feedback`, `GET /api/survey-analysis`를 제공한다. 핵심 조건 70점·설문 대응 10점·AI 상황 해석 20점의 기존 점수 의미를 유지하며, 입력값을 바꾸는 동안에는 Gemini를 호출하지 않고 분석 요청 시에만 호출한다. FastAPI는 `app.py`와 Streamlit을 import하지 않는다.

### 로컬 실행

```bash
pip install -r requirements.txt
uvicorn main:app --reload --port 8000

# 새 터미널
cd frontend
npm install
npm run dev
```

`frontend/.env`에는 `VITE_API_BASE_URL=http://localhost:8000`, 백엔드 `.env`에는 `GEMINI_API_KEY`를 설정한다. API 키는 React 코드에 넣지 않는다.

기존 Streamlit 화면을 로컬에서 별도로 확인할 필요가 있을 때만 `pip install -r requirements-streamlit.txt` 후 `streamlit run app.py`를 실행한다. 이 패키지는 Render 운영 서버에 설치하지 않는다.

### Render 배포

저장소 루트의 `render.yaml`을 Blueprint로 적용하거나 서비스를 각각 만든다.

- 백엔드 Web Service: `pip install -r requirements.txt` / `uvicorn main:app --host 0.0.0.0 --port $PORT` / Health Check `/health` (Streamlit 미사용)
- 프론트 Static Site: Root Directory `frontend`, `npm ci && npm run build`, Publish Directory `dist`
- 백엔드 환경변수: `GEMINI_API_KEY`, `GEMINI_MODEL`, `FRONTEND_ORIGIN`
- 프론트 환경변수: `VITE_API_BASE_URL`
